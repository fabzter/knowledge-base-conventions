# Knowledge Base Lifecycle

## What a more complete PARA practice adds

The folder model already contains all four PARA categories. "Lightweight" describes the implementation and maintenance burden; it does not mean Projects, Areas, Resources or Archives were omitted.

A more mature practice clarifies commitments and keeps information useful as its purpose changes. The routines below are this system's recommended operating conventions, not additional mandatory steps claimed to be part of an official PARA certification.

Do not add folders to demonstrate completeness. Do not reorganize existing notes automatically. Add a convention only when it reduces a repeated retrieval or execution problem.

## 1. Capture without prematurely designing a taxonomy

- Put unclassified material in `00_inbox` with enough source/date context to understand it later.
- Distinguish raw capture from a finished interpretation. A pasted transcript is not an observed lesson.
- Use a known project home directly when ownership is clear; Inbox is not a mandatory detour.
- Capture a next action in the existing task/project system, not in an invented parallel tracker.

## 2. Define an active project by its outcome

A project note should answer:

- What outcome are we trying to produce?
- What would make it done, paused or withdrawn?
- What is the current state and its authoritative tracker?
- What is the next concrete action or decision?
- Which Area does this support, and which source/resource/people notes are needed?

A target date is useful when real; do not invent one merely to fill a field. "Career" is an Area. "Complete the current search and accept a suitable role" is a finite project. Company processes can be subprojects with their own ownership and state inside that effort.

## 3. Maintain an Area by a standard, not an endless project

An Area note describes an ongoing responsibility and the standard worth maintaining. Link current projects that support it, concerns that need attention and reusable personal context.

Examples: maintain a healthy home, keep financial records current, develop professional capabilities. These do not become completed simply because one supporting project finishes.

## 4. Use Resources for knowledge, not a waiting room for all files

- Keep references that have a plausible future use.
- Write focused explanations in your own words with source links.
- Link a Resource into an active project rather than copying it repeatedly.
- Keep personal, ongoing operating context in its Area when that is its real owner.
- Separate source notes, reusable interpretation and project-specific application.

## 5. Review at a sustainable cadence

A short weekly review is a suggested starting point, not a scheduled automation:

1. Classify useful Inbox captures; discard only with appropriate authorization.
2. Scan the active project list for missing outcomes, next actions and decisions.
3. Identify projects that are complete, paused or no longer being pursued.
4. Extract only the lessons worth reusing; do not summarize every note for the sake of it.
5. Repair a broken reading path when it actually obstructs work.

A less frequent Area review can check whether responsibilities and standards still reflect real life. Adjust cadence to actual use. These suggestions do not create calendar events, reminders or cron jobs.

## 6. Close a project deliberately

Before an authorized archive move:

- Record its actual outcome and closure reason without inventing success.
- Resolve or explicitly leave open the remaining actions.
- Preserve historical briefs, debriefs, source evidence and decision dates.
- Extract a reusable lesson into the owning Area or Resource and link back to evidence.
- Leave a discoverable pointer from the Area/project index.
- Use a link-aware move into `04_archive`, preserving a useful relative ownership structure.
- Verify notes, attachments, links and source retention after the move.

An inactive project may still hold reference value. Archive is not a trash can. A paused project can be reactivated with its context intact.

## 7. Change filing when purpose changes

PARA is about actionability, so material can move as its role changes. That is a classification decision, not a nightly housekeeping rule.

If a Resource becomes central to active work, usually link it from the Project first. If a whole project ends, archive the project together rather than scattering its history. If a repeated placement question reveals ambiguity, improve the convention or navigation before attempting a bulk migration.

## What not to automate

The governance sync updates documentation only. It does not classify the Inbox, promote sources into Resources, archive projects, rewrite briefs, infer private status or make calendar commitments. Those operations involve judgment and require their own explicit task scope.
